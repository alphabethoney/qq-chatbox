# 历史隐私处理与协作要求

## 范围与方法

本次采用逐提交净化，保留开发演进顺序和合并关系，不将历史压缩为单一初始提交。重写范围为处理时公开的 `main` 全部可达提交；处理时未发现其他公开分支或标签。已审查 34 个历史提交、114 个历史文件路径和 233 个唯一文件内容对象；均为 UTF-8 文本，未发现历史数据库、媒体或压缩包。

- 对已识别的私人账号、称谓、部署用户/路径、主机地址及个体运行背景替换或泛化。
- 对历史文件内容、路径及提交说明应用规则；作者与提交者统一为项目贡献者通用身份。
- 保留合成测试、协议常量及公开依赖链接，不把它们误当作个人凭据。
- 不上传本地历史备份、聊天数据、密钥、人物档案、索引或其他工作分支；私有备份不可作为发布源。
- 最终仍需用源码测试、全历史规则复扫和远端引用核验验证，而非仅检查最新文件。

## 不能保证的事项

逐提交净化是对已识别内容的处理，不是无法重新识别个人的数学保证。公开仓库归属仍然可见；未识别的间接线索、已有下载、平台缓存及第三方副本可能残留。历史重写不会撤回已发送给模型服务的文本，也不会自动撤销已经暴露的凭据。

托管平台可能仍通过旧提交标识、拉取请求引用或缓存展示旧内容。应通过平台支持渠道申请敏感数据清理，必要时请求旧引用清除、服务端对象回收及缓存清除；平台是否受理和处理结果不能由本地 Git 命令保证。参见 [GitHub 敏感数据移除说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)。

## 协作者操作

1. 停止从旧克隆推送；重新克隆清理后的仓库。
2. 不要把旧分支 merge/pull 回新历史，不要使用 `push --all`、`push --mirror` 或批量上传旧标签。
3. 尚未发布的工作应先在私有环境检查差异、去除敏感信息，再移植至新克隆；不要直接上传旧提交链。
4. 清查个人克隆、分叉、备份和附件。需要保留的敏感备份应离线存储并限制访问；不用的副本按组织的数据销毁流程处理。
5. 对已暴露且仍有效的 API 密钥、访问令牌或密码按产品流程撤销/轮换。数据库密钥不同于普通令牌，变更前应确认备份、重加密及恢复能力，避免丢失合法解密能力。

## 防止再次提交

默认忽略索引、数据库、口令产物与历史备份；但 `.gitignore` 不影响已跟踪文件，也不能阻止 `git add -f`。每次发布应检查暂存文件、提交说明和作者身份，避免把原始日志、会话截图或私有运行报告复制进源码和文档。凭据插件可能输出敏感口令，其终端日志同样不得公开。
